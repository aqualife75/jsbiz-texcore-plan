# 작성 규칙 — 블록 형식·라벨·순서·금지 (tp-writer · tp-researcher merge 공통)

## 1. 작성 순서 ≠ 제출 순서 (KoEF AI 사계서 작성법, 2026.04)
양식은 Ⅰ-1부터지만 그 순서로 쓰면 고객이 모호한 채 동기와 BM이 공중에 뜬다. **쓰는 순서**:
1. Ⅰ-2b 목표 고객 → Ⅰ-2a 컨셉(문제·해결 방식) → Ⅰ-2c 차별성 → Ⅰ-2d 시장
2. Ⅱ-1 핵심기술(세 문장) → Ⅱ-2 IP·TRL·업그레이드
3. Ⅲ-1 시제품(가설→단계→방법→비용→성공 기준) → Ⅲ-2 일정(◆ 마일스톤·숨은 일정·첫 고객) → Ⅲ-3
4. Ⅳ 팀(역할 = 위 계획의 담당자)
5. **마지막에 Ⅰ-1 동기·목표**(위에서 확정된 가설·검증 계획을 텍스코어 프로그램 흐름에 얹는다 → 참여의지·프로그램 이해도 20점)
6. 영문 Summary(해외형) — Ⅱ-1·Ⅰ-2·Ⅰ-2c를 영어로 압축
제출 순서(JSON `sections` 배열 순서)는 양식 순서로 되돌린다.

## 2. 섹션 구조 — "결론 박스 → 소제목 → 증거 그림 → 짧은 문단"
모든 본문 섹션(S_I1·S_I2·S_II1·S_III1·S_III2)은 이 순서를 지킨다.
1. **`callout`(한 줄 결론)**: 심사위원 질문에 대한 답 한 문장(숫자 포함). 80자 이내. 섹션의 첫 블록. 예) "하지마비 환자 3만 명이 스스로 서서 걷는 재활 훈련을 받지 못하는 문제를, 피부 부착 센서 없이 의도를 읽는 로봇으로 해결합니다."
2. **`heading`(□ 소제목)**: 양식 소제목을 그대로 또는 다듬어서(□ 창업(탐색) 아이템의 컨셉 등). 소제목은 질문의 답이 보이게 바꿔도 된다("□ 목표 고객 — 재활병원 치료사(1차)·환자 보호자(2차)").
3. **증거 그림/표(`figure`·`figure_ref`·`table`)**: 소제목마다 1개 이상. 글보다 먼저 배치(심사위원이 그림을 먼저 보고 글로 확인). 규칙은 `visual_rules.md`.
4. **`para`/`bullets`**: 문단은 3~4문장(420자 이내), 불릿은 한 줄 140자 이내 6개 이하. 개요식(불릿·표)을 기본으로 하고 서술형 문단은 소제목당 1개까지.
5. 숫자가 나오는 문장은 **괄호 출처** 또는 표 아래 출처줄. 형식: `(출처: 발행처 「제목」, 기준 YYYY.MM)`.

## 3. 블록 타입(04_draft_v1.json / 07_draft_v2.json)
| type | 필드 | 규칙 |
|---|---|---|
| callout | text | 섹션 첫 블록. 결론 한 문장, 숫자 1개 이상, 80자 이내 |
| heading | text | "□ "로 시작, 40자 이내 |
| subheading | text | "∎ "로 시작, 50자 이내 |
| para | text, kind, calc? | 420자 이내, 문장 80자 이내 |
| bullets | items[], kind | 항목 140자 이내, 6개 이하. 항목은 "주어+숫자+결과" 구조 |
| table | caption, columns, rows, col_widths_mm?, source, font_pt? | 캡션 "[표 n] …", 7열·12행 이내, 셀 90자 이내, 출처줄 |
| figure | caption, images[{path,width_mm}], source, proves | 팀 자료 이미지 직접 삽입. 캡션 "[그림 n] …", 출처, "→ 증명: …" 필수 |
| figure_ref | figure_id, caption, source, proves | `figures[]`에 정의한 생성 도식 참조(tp-designer가 data를 채움) |
| spacer | — | 빈 줄(남용 금지) |
`kind`: fact(사실 팩·증거에 있음) / estimate(계산·추정, `calc` 산식 필수, 본문에 "[추정]") / plan(계획·목표, 본문에 "[목표]"·"예정"·"계획"이 드러나야 함).

## 4. 라벨(본문 문자열에 그대로 쓴다)
- `[자료 없음]` — intake가 슬롯에 표시. 본문엔 쓰지 않는다.
- `[기입 필요: 항목]` — 팀만 아는 사실(PM 연락처·특허번호·생년월일·첫 고객 이름 등). v1에서 허용, **v2에는 남으면 안 됨**(팀 답변으로 채우거나 `[확보 필요]`로 옮기고 `to_secure[]`에 기록).
- `[추정]` — 사실을 근거로 계산한 값. `calc`에 산식("280개 × 50만 원 × 12개월 = 16.8억").
- `[목표]` — 팀이 세운 목표치(시제품 성능·매출·인터뷰 건수).
- `[확보 필요]` — 조사로도 못 채운 것. `to_secure[]`에 항목·이유·섹션.

## 5. 절대 규칙
1. **사실 팩·증거 원장에 없는 숫자를 만들지 않는다** — `harness trace`가 잡는다. 전화번호·특허번호·경력도 팀 자료 전사만.
2. **팀 내부 사실(고객 인터뷰·시제품·팀 경력·첫 고객·가격 결정)은 외부 조사로 대체하지 않는다.** 없으면 사실대로 쓰고 Ⅲ에 검증 계획으로 돌린다.
3. 형용사 대신 숫자. 기능 나열 금지. 한 칸 = 심사위원 질문 하나 = 답 하나.
4. `assets/banned_phrases.json`의 금지 표현은 validate가 막는다. 경고 표현(플랫폼·생태계·고도화·다양한·효율적…)은 섹션당 2회까지.
5. 비교·차이·의미는 **고객에게 생기는 변화**로 끝난다(시간·비용·횟수·회수 기간).
6. 트렌드 키워드(AI·디지털헬스·기후테크·딥테크·시니어테크·K-콘텐츠·글로벌·지역)는 **진정성 근거 4개(기술/데이터/파트너/경험) 중 2개 이상**이 사실 팩에 있을 때만 아이템명·Ⅰ-2 첫 문단에 쓴다(biz-mentor judge-preferences). `outline.trend_label.use`로 기록.
7. 쪽 예산(`assets/limits.json`)을 넘기면 validate가 막는다. 줄일 때는 문장 삭제보다 **문단 → 표/그림으로 치환**이 먼저.
8. 윤리: 산출물은 초안이다. 팀(EL)이 마지막으로 읽고 고쳐야 할 항목을 `팀_확인사항.md`에 남긴다(대필 금지 원칙, biz-mentor G).

## 6. 톤
"~입니다/~합니다" 체(Ⅲ 일정·표 안은 명사형 허용). 친근하지만 전문적. 제목·결론은 결론이 드러나는 문장. 심사위원이 비전문가일 수 있으므로 `plain_language.md`를 따른다.

## 7. 영문 Summary(해외교육형) 규칙
- 각 500자(공백 포함 characters) 이내. 1) 기술: 무엇을 가능하게 하는지 먼저, 사양은 뒤 2) 문제·고객: 미국 고객 세그먼트를 명시(예: outpatient rehab clinics in the US) 3) 차별: 비교 대상 실명 + 숫자.
- 미국 시장 적합도 P/F 대비: Ⅰ-2d에 미국 시장 수치·규제(FDA 등급·FCC·UL 등) 1줄, 첫 인터뷰 대상 유형 1줄을 넣는다.
